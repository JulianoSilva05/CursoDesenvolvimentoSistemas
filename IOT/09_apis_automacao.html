Quando o app não é suficiente

Limites do app

  • Precisa rodar 24/7 (monitoramento)
  • Precisa armazenar muito dado
  • Precisa integrar com vários sistemas
  • Precisa de regras complexas e logs

Entra o “backend”

  • Serviço de ingestão (HTTP/MQTT)
  • Banco de dados (séries temporais ou relacional)
  • Processamento (alertas, agregações)
  • API para apps e dashboards

Bloom (Criar): o objetivo agora é construir “cola” entre sistemas com qualidade e testabilidade.

Integração por MQTT (conceito de consumidor)

Ideia (independente de linguagem): - conectar ao broker - assinar tópicos de telemetria - validar payload - armazenar e/ou disparar alerta Exemplo de tópico: iot/senai/lab1/esp32-01/telemetry

Prática: mesmo sem rodar código aqui, você deve saber desenhar as funções, entradas, saídas e testes.

API HTTP para telemetria (design simples)

Rotas mínimas

POST /api/telemetria GET /api/dispositivos/{id}/ultimo GET /api/dispositivos/{id}/historico?from=&to=

Validações

  • deviceId obrigatório
  • ts obrigatório e plausível
  • métricas em faixas válidas
  • limitar tamanho do payload

Consistência: padronize nomes e unidades. Trocar temp por temperature no meio quebra tudo.

Testes: o que deve ser provado

Casos mínimos

  • Payload válido → 200 OK
  • Falta deviceId → 400
  • ts inválido → 400
  • valor fora de faixa → 422
  • duplicidade (mesmo id/ts) → idempotência

Qualidade (não funcional)

  • Logs úteis (sem vazar segredo)
  • Rate limit (não travar)
  • Resposta rápida (timeouts controlados)
  • Monitoramento (status, métricas)

Atividade 1 (4h): Especificação de API (contrato)

⚠️ Importante: Atividade INDIVIDUAL. Não saia desta tela. Entregue pelo botão de envio.

Requisitos

  • Definir payload do POST /api/telemetria
  • Definir respostas (200/400/422/500)
  • Definir autenticação (token)
  • Definir idempotência (evitar duplicidade)

Entregue

Escreva o “contrato” com exemplo de request/response e regras de validação.
