O que é Teste de Usabilidade (de verdade)

Definição prática

Teste de usabilidade verifica se uma pessoa consegue concluir tarefas com eficiência, sem se perder e sem cometer erros graves em uma interface.

  • Efetividade: concluiu ou não concluiu?
  • Eficiência: quanto tempo/cliques?
  • Satisfação: foi confortável? faz sentido?

O que NÃO é

  • Não é “gostar da cor”.
  • Não é só “o layout está bonito”.
  • Não é só “tem CSS”.

Visual ajuda, mas usabilidade é sobre resultado: o usuário consegue fazer o que veio fazer.

Teste de Navegação: o usuário não pode se perder

Teste de navegação valida se a pessoa consegue ir e voltar entre telas sem confusão, mantendo o contexto.

Perguntas que sempre fazemos

  • Como o usuário chega na funcionalidade?
  • Existe um caminho claro para voltar?
  • O sistema informa onde ele está (título, breadcrumb, menu)?
  • O usuário entende o que acontece após clicar?

Falhas típicas

  • Links que não levam a lugar nenhum.
  • Botões com nomes confusos (“OK” para tudo).
  • Sem feedback após enviar formulário.
  • Erro sem explicação (“Falha” sem dizer por quê).

Dica de professor: navegação é fluxo. Se o fluxo não está claro, o sistema “funciona” mas não “serve”.

Casos de Uso: transformando requisitos em tarefas testáveis

Por que o caso de uso ajuda na usabilidade

O caso de uso descreve o objetivo do usuário e a interação esperada com o sistema. Ele vira um roteiro de teste:

  • Quem é o ator?
  • Qual é a meta?
  • Qual o fluxo principal?
  • Quais exceções? (erro/validação)

Como usar na prática

Para cada caso de uso, você cria:

  • Uma tarefa observável (o que o usuário faz).
  • Critério de sucesso (o que deve acontecer).
  • Checklist de navegação (entrar/sair/voltar).
  • Regras de erro (mensagens, validações).

Observe: o usuário não “testa SQL”. Ele testa tarefas: cadastrar e consultar. O resto é responsabilidade do sistema.

Do Caso de Uso para Requisitos Funcionais (RF)

Um requisito funcional descreve o que o sistema deve fazer. Do caso de uso, extraímos RFs claros.

RF01: O sistema deve permitir cadastrar produto com: nome, preço, código de barras, marca e categoria. RF02: O sistema deve validar campos obrigatórios antes de salvar. RF03: O sistema deve impedir preço negativo e informar erro. RF04: O sistema deve confirmar o cadastro com mensagem de sucesso. RF05: O sistema deve permitir consultar produtos cadastrados.

Como “ver” usabilidade no RF

  • RF não é só função: inclui feedback (sucesso/erro).
  • Se o usuário não entende a mensagem, a função falha na prática.
  • Validação é usabilidade quando evita tentativa e erro.

O que vira caso de teste

  • Entrada válida → salva e confirma.
  • Campo vazio → impede e explica.
  • Preço inválido → impede e orienta.

Checklist rápido de Usabilidade (aplicável em qualquer sistema)

Clareza e linguagem

  • Títulos informam onde estou?
  • Botões descrevem ação (“Salvar”, “Cancelar”)?
  • Mensagens de erro dizem o que fazer?

Eficiência e consistência

  • Fluxo tem passos desnecessários?
  • Campos usam tipos corretos (number, email)?
  • Mesma ação tem o mesmo comportamento em telas diferentes?

Prevenção de erros

  • O sistema impede dados inválidos antes de enviar?
  • Existe máscara ou exemplo (placeholder) quando necessário?
  • O usuário consegue desfazer (voltar) sem perder tudo?

Acessibilidade básica

  • Contraste suficiente?
  • Labels associados aos campos?
  • Teclado navega bem (tab, enter)?

Atividade 1: Caso de Uso “bate” com o sistema?

⚠️ Importante: Atividade INDIVIDUAL. Use “Dividir Tela” para consultar os slides enquanto escreve.

Enunciado

Escolha um software real para analisar (ex.: um site de matrícula, um sistema de biblioteca, um e-commerce ou um sistema escolar). Em seguida:

  • Desenhe (no papel ou em ferramenta) um diagrama de caso de uso simples do sistema (2 atores e 6 casos de uso).
  • Faça a verificação: cada caso de uso do diagrama existe e funciona no sistema?
  • Identifique lacunas: funcionalidades importantes do sistema que não aparecem no diagrama.
  • Identifique excesso: casos no diagrama que não existem ou não fazem sentido.

O que entregar

  • Nome do software analisado + objetivo do usuário
  • Lista dos atores e dos 6 casos de uso
  • 5 verificações “bate/não bate” (com evidência: print ou descrição objetiva)
  • 3 melhorias no diagrama (o que você adicionaria/removeria/ajustaria)

Atividade 2: Diagrama de Navegação (na mão) e validação do fluxo

Enunciado

Escolha o mesmo software da Atividade 1 e desenhe um diagrama de navegação (fluxo de telas) à mão. Depois, navegue no sistema para verificar se o fluxo desenhado acontece de verdade.

  • Desenhe de 6 a 10 telas (caixas) e conecte com setas (ações do usuário).
  • Marque 2 pontos de retorno (voltar/cancelar) e 2 pontos de erro (validação).
  • Teste no sistema: existe link/botão para cada transição?
  • Registre onde o usuário fica “preso” (beco sem saída) ou se perde.

Dicas

  • Use nomes claros de telas: “Login”, “Home”, “Lista”, “Detalhe”, “Formulário”, “Confirmação”.
  • Para validar usabilidade, observe: texto dos botões, feedback e consistência.
  • Se o sistema tem menu, ele deve aparecer onde o usuário precisa.
