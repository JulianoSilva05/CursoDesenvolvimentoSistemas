Bug report: como escrever para ser resolvido

Campos essenciais

  • Título claro (o que quebra)
  • Ambiente (navegador, versão, URL)
  • Passos para reproduzir
  • Resultado atual vs esperado
  • Evidência (print/log)

Princípio

Um bom bug report permite que outra pessoa reproduza em menos de 2 minutos.

Severidade x Prioridade

Severidade (impacto)

  • Crítico: impede uso / perde dados
  • Alto: quebra fluxo principal
  • Médio: problema com workaround
  • Baixo: detalhe / cosmético

Prioridade (ordem de correção)

Nem todo bug crítico é prioridade alta se não afeta o release atual, mas em geral bugs críticos sobem rápido.

Relatório de testes (o que um gestor precisa saber)

Resumo

  • O que foi testado
  • O que não foi testado
  • Quantidade de casos: pass/fail/block
  • Principais riscos

Decisão

O relatório deve ajudar a responder: “podemos publicar?” e “qual risco aceitamos?”.

Guia: do sistema ao banco, interface e bateria de testes

1) Modelar e persistir

  1. Liste requisitos (UML: casos de uso + classes ou DER).
  2. Crie o banco (MySQL): tabelas, chaves, índices básicos.
  3. Conecte a aplicação (PHP PDO / Java JDBC / Python + driver) com prepared statements.

2) Interface e fluxo

  1. Prototipe telas (HTML/CSS ou Swing/JavaFX).
  2. Implemente CRUD mínimo e mensagens de erro claras.
  3. Registre fluxo principal e alternativas (para virar casos de teste).

3) Testar em camadas

  • Fumaça: build sobe, login abre, CRUD básico responde.
  • Funcional: regras de negócio e validações.
  • Integração/API: persistência e endpoints.
  • Desempenho: consultas com volume (N registros).
  • Segurança: SQLi, XSS, sessão.
  • Usabilidade/UAT: tarefas com usuário real ou roteiro.

4) Evidências e encerramento

Guarde prints, logs ou vídeos curtos. Feche com relatório (pass/fail, riscos, go/no-go) e bugs linkados aos casos de teste.

Atividade 1: Criar um bug report completo

⚠️ Atividade INDIVIDUAL.

Cenário

Ao cadastrar produto sem preço, o sistema salva mesmo assim e quebra a listagem depois.

Entrega

Escreva um bug report completo (título, ambiente, passos, atual, esperado, severidade, prioridade, evidência).

Atividade 2: Relatório final da disciplina

Enunciado

Monte um relatório curto (1 página) como se você fosse o responsável pelos testes de um sistema de cadastro.

Obrigatório

  • Escopo testado e não testado
  • Métricas: pass/fail/block
  • Top 3 riscos
  • Recomendação (go/no-go) e por quê

Atividade 3: Plano de testes do seu mini-sistema (Criar)

⚠️ INDIVIDUAL. Descreva um sistema que você poderia implementar (PHP+MySQL ou Java+MySQL ou Python+SQLite). Não precisa rodar agora; o foco é o plano de testes.

Entregue no texto

  • 5 casos de teste de fumaça (bullet com passo + esperado).
  • 8 casos de teste funcional (2 negativos).
  • 3 casos de integração (BD ou API).
  • 2 cenários de desempenho (o que medir: tempo, N usuários).
  • 3 vetores de segurança (ex.: SQLi em campo X).
  • Roteiro de usabilidade (3 tarefas + critério de sucesso).
  • Checklist de UAT (quem homologa, ambiente, critério go/no-go).

Dica

Use os modelos das aulas 02 e 05. Numere CT01, CT02… e cite qual RF cada um cobre.

Encerramento da Disciplina

Você percorreu a taxonomia de Bloom aplicada a QA: desde lembrar conceitos até criar planos e relatórios. Requisitos, fumaça, funcional, integração, automação, desempenho, usabilidade, segurança, UAT, defeitos e projeto integrado passam a fazer parte do seu repertório técnico.
